## 🔴 KRITISCHE BUGS (vor Phase-5-Rollout fixen)

### BUG-NS-1 — `asOfDate` Query-Parameter wird ignoriert (Invariante I10)

**Symptom:**
`GET /api/budget/203047/overview?asOfDate=2026-01-15` liefert **byte-identische** Antwort zu `?asOfDate=2026-12-31`. Beide zeigen Werte von **today**.

**Live-Beweis** (Cust 203047, alle 5 Stichtage liefern dasselbe):
```
2026-01-15: currentYearAllocatedCents=78600
2026-03-15: currentYearAllocatedCents=78600
2026-05-31: currentYearAllocatedCents=78600
2026-06-02: currentYearAllocatedCents=78600
2026-12-31: currentYearAllocatedCents=78600
```

**Erwartet** (lt. Invariante I10 — Temporal correctness):
```
2026-01-15: 13100 (1 Monat)
2026-05-31: 65500 (5 Monate)
2026-12-31: 157200 (12 Monate)
```

**Impact:** Stichtags-Auswertungen, Monatsabschluss-Reports, „Verbrauch zum Quartalsende" — alle liefern falsche Werte. Wenn das Reporting-System darauf baut, sind alle historischen Reports verfälscht.

**Code-Pointer:** `server/routes/budget.ts` `GET /:customerId/overview` — Parameter wird vermutlich nicht an `unified-reader` weitergereicht.

**Fix:** `req.query.asOfDate` parsen, an `unified-reader.getBudgetSummary*(customerId, asOfDate)` weiterleiten, dort als `transactionDate` für allocation-historization verwenden.

**Priorität:** 🔴 **BLOCKER** — verletzt Kern-Invariante I10.

### BUG-NS-2 — Hard-Block bei Overdraft nicht aktiv (Invariante I5)

**Symptom:**
Customer mit `acceptsPrivatePayment=false` + verfügbarem Budget 947€. Termin mit 30h Alltagsbegleitung (1260€) gebucht → **Status 201 Created** + Soft-Warning-Feld `_warning: "Achtung: Geplante Termine übersteigen §45b um 355,00 €."`

**Erwartet** (lt. North-Star §"Private/Selbstzahler" + Invariante I5):
```
Status 403 Forbidden / 422 Unprocessable
Body: {error: "BUDGET_INSUFFICIENT", message: "...", ...}
```

**Live-Beweis:** Termin 338934 angelegt, `availableAfterPlannedCents: -31300` (negativ!). Server gibt kein Veto.

**Diagnose:** `BUDGET_HARD_HOLDS` Feature-Flag auf Replit-Dev **AUS**. Die Routen prüfen `if (hardHoldsEnabled()) ...` — aus = keine Reservierung = kein Block.

**Fix-Optionen:**
- **(A)** Flag `BUDGET_HARD_HOLDS=1` setzen auf Replit-Dev (+ Equality-Verifier vorher laufen lassen)
- **(B)** Zusätzlich: auch bei Flag-Aus eine *Sanftere* Pre-Validation in `appointments.ts` einbauen, die wenigstens bei `availableAfterPlanned < 0` und `acceptsPrivatePayment=false` mit 422 antwortet

**Priorität:** 🔴 **BLOCKER** für Phase-5-Rollout — sonst wird das ganze Hard-Hold-Versprechen leer.

### BUG-NS-3 — §45a `monthlyBudgetCents = 0` trotz PG 2

**Symptom:**
Customer PG 2, §45a `enabled=true`, `isCurrentlyActive=true`, aber `monthlyBudgetCents=0`. Lt. SGB XI §45a hat PG 2 Anspruch auf 40% des Sachleistungsbetrags = **318 €/Monat** (oder mehr bei PG 3-5).

**Live-Beweis** (Cust 203047, alle 5 Stichtage):
```
umwandlung45a: {
  isCurrentlyActive: true,
  monthlyBudgetCents: 0,
  currentMonthAllocatedCents: 0,
  currentMonthAvailableCents: 0
}
```

**Diagnose:** Bei PUT type-settings habe ich kein `monthlyLimitCents` für §45a gesetzt. Vermutlich erwartet die Logik einen expliziten Wert, statt vom PG abzuleiten.

**Im Code (vermutlich):** §45a-Auto-Allocation aus PG nicht implementiert. Statt 40% × `BUDGET_45A_MAX_BY_PFLEGEGRAD[pflegegrad]` automatisch zu setzen, wird der eingegebene `monthlyLimitCents` 1:1 verwendet → null wird zu 0.

**Fix:** In `unified-reader` oder `cap-calculator` §45a-Default = `BUDGET_45A_MAX_BY_PFLEGEGRAD[customer.pflegegrad]` setzen, wenn `monthlyLimitCents` null ist.

**Priorität:** 🟡 **HOCH** — affects all customers PG 2-5 who don't manually configure §45a. Likely already affects production.

### BUG-NS-4 — `monthlyLimitCents` in Overview NULL obwohl gesetzt+wirksam

**Symptom:**
Nach `PUT /api/budget/:cid/type-settings` mit `monthlyLimitCents: 4200`:
- `currentYearAllocatedCents` sank von 78600 → 69700 (Cap wirksam, Juni-Monat auf 4200 statt 13100 reduziert ✅)
- `monthlyLimitCents` in Overview-Response: **null** ❌

**Erwartet:** Overview zeigt `monthlyLimitCents: 4200`.

**Impact:** UI weiß nicht dass ein Cap aktiv ist → User sieht reduzierten Allocated-Wert ohne Grund → Vertrauensverlust.

**Code-Pointer:** Overview-DTO-Building in `summary-queries.ts` oder `unified-reader.ts` — Cap aus `customer_budget_type_settings` wird nicht ins DTO durchgereicht.

**Priorität:** 🟡 **MITTEL** — UX-Bug, keine Datenkorruption.
