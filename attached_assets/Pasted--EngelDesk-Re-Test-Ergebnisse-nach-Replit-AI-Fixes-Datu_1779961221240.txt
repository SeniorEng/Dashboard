### ✅ BUG-1 GEFIXT: Doppel-Allokation §45a + §39

**Reproducer ausgeführt** auf Kunde 153082 (PG4 Pflegekasse_gesetzlich):

1. `POST /api/budget/153082/initial-budget` für §45a (74360 Cents) → 201
2. `POST /api/budget/153082/initial-budget` für §39 (353900 Cents) → 201
3. `PUT /api/budget/153082/type-settings` mit `monthlyLimitCents=74360` für §45a und `yearlyLimitCents=353900` für §39 → 200
4. `GET /api/budget/153082/overview`

**Ergebnis:**

```json
{
  "umwandlung45a": { "currentMonthAvailableCents": 74360 },
  "ersatzpflege39_42a": { "currentYearAvailableCents": 353900 }
}
```

**Vorher:** 148720 (doppelt) / 707800 (doppelt). **Jetzt:** korrekte Einzelwerte 74360 € / 353900 €. **`u45a_doubled: false, e39_doubled: false`** verifiziert.

### 🔴 BUG-9 NOCH OFFEN: Phasen-Historisierung defekt

**Reproducer:** 4 sequenzielle `PUT /api/budget/153082/type-settings` mit unterschiedlichen `validFrom` (2026-06-01: 65,50€ → 2026-08-01: 80€ → 2026-10-01: 100€ → 2027-01-01: 131€).

**Erwartet:** 4 Zeilen in `customer_budget_type_settings` für `entlastungsbetrag_45b`, 3 davon mit `validTo` der jeweiligen Folge-Phase, eine offen.

**Ergebnis:**
```json
[
  {"limit": 13100, "validFrom": "2027-01-01", "validTo": null}
]
```
**Nur 1 Zeile.** Die ersten 3 Phasen sind komplett verloren — Append-Only-Historisierung greift nicht bei explizit gesetztem `validFrom`. Dies blockiert das gesamte Anwendungsfall „Anteil ändert sich über die Zeit" (z.B. „Kunde gesteht uns von Juni–Juli 50% des §45b zu, ab August 80%").

**Status:** Wie im Original-Report — keine Änderung sichtbar.

### 🟡 BUG-10 TEILWEISE GEFIXT: Cascade-Transaktion §45a

**Reproducer:** 4h Hauswirtschaft (152 €) auf Kunde 153082 mit erschöpftem §45b → Cascade auf §45a.

**Ergebnis:**
```json
[
  {"bt":"entlastungsbetrag_45b", "amt":-7900,  "alloc":109438, "hwCents":7900},
  {"bt":"umwandlung_45a",        "amt":-7300,  "alloc":109439, "hwCents":null}
]
```

- ✅ **`allocationId=109439`** (vorher null) — Cascade-Folge-Tx wird jetzt korrekt einer Allokation zugeordnet
- 🔴 **`hauswirtschaftCents=null`** — der proportionale Service-Anteil wird weiterhin nicht aufgeteilt

**Folge:** Drift-Detektoren wie `tests/equality/*` würden bei Σ(hauswirtschaftCents) = 7900 (≠ 15200 = appointment.hwCents) immer noch rot. Lexware-Export und Statistiken aggregieren nur die §45b-Zeile.

### 🔴 AUDIT HOCH-2 NOCH OFFEN: §45a für PG<2 zugelassen

**Reproducer:** Kunde 153211 angelegt mit `pflegegrad=1`, `billingType=pflegekasse_gesetzlich`. Versuch:

```javascript
fetch('/api/budget/153211/initial-budget', {method:'POST', ..., body: JSON.stringify({
  budgetType:'umwandlung_45a',
  currentYearAmountCents: 31840,
  budgetStartDate: '2026-05-28'
})})
// IST: 201 "Startbudget erfolgreich erfasst"
//      Allokation angelegt: id=109536, year=2026, month=5, amount=31840, source=initial_balance
// SOLL: 400/409 + "§45a Umwandlungsanspruch ist erst ab Pflegegrad 2 verfügbar"
```

`clampToStatutoryMax` aus `shared/domain/budgets.ts:65-76` validiert diesen Fall bereits korrekt mit der erwarteten DE-Meldung — aber der `initial-budget`-Endpoint ruft die Funktion nicht auf oder ignoriert ihren Return.

**Status:** Wie im Original-Audit-Chunk 07 dokumentiert. Selbstzahler-Validierung (BUG-6) zeigt, dass das Pattern „bei nicht zulässigem Topf 409 mit DE-Fehler" möglich ist — sollte für §45a/PG<2 analog implementiert werden.

### 🆕 BUG-12 NEU: Type-Settings akzeptiert für Selbstzahler ohne Reject

**Beobachtung:** Selbstzahler-Kunde 153210 hat trotz BUG-6-Fix immer noch:
```json
[
  {"budgetType":"entlastungsbetrag_45b", "enabled": true,  "monthlyLimitCents": null},
  {"budgetType":"umwandlung_45a",        "enabled": false, "monthlyLimitCents": null},
  {"budgetType":"ersatzpflege_39_42a",   "enabled": false, "monthlyLimitCents": null}
]
```

**Ursache:** `PUT /api/budget/:cid/type-settings` mit `enabled=true` für §45b für einen Selbstzahler-Kunden wurde **201** akzeptiert. Erst der nachfolgende `initial-budget`-Call greift mit 409.

**Inkonsistenz:** Eine Settings-Zeile mit `enabled=true` für einen Topf, der für diesen Kunden „nicht verfügbar" ist, ist semantisch widersprüchlich.

**Empfehlung:** Selbstzahler-Check auch in `upsertBudgetTypeSettings` einbauen, mit gleichem `BUDGET_NOT_AVAILABLE_FOR_SELBSTZAHLER`-Fehlercode.
