## Fehler 2 — tests: 22 Dateien / 39 Tests + 2 Snapshots rot

**Log-Summary:** `Test Files 22 failed | 377 passed` · `Tests 39 failed | 2864 passed` · `Snapshots 2 failed` → exit 1.

**Cluster A — Architektur-Guard `tests/architecture/soft-delete-coverage.test.ts` (3 rot):**
- „Storage-Module dürfen kein `db.select().from(<soft-deletable-Tabelle>)` direkt nutzen"
- 2× Snapshot „pro Routen-/Storage-Datei nur Repo-vermittelte Reads registriert" (`repoUsageSnapshot(STORAGE_ROOT)`)

→ Der #1584-Change hat einen **direkten Select auf eine soft-deletable Tabelle in einem Storage-Modul** eingeführt (verletzt die Soft-Delete-Disziplin — genau das Thema des Drafts #1550).
**Fix:** den direkten `db.select().from(...)` durch den **Repo-vermittelten Read** ersetzen (Muster, das der Guard erzwingt). Erst danach die 2 Registrierungs-Snapshots aktualisieren — **nur** wenn der neue Read-Satz beabsichtigt ist, nicht blind `-u`.

**Cluster B — breite Stunden-Assertions (Rest der 39):**
→ Der Urlaub/Krankheit-Stunden-Change hat viele erwartete Stundenwerte verschoben.
**Fix:** Vitest lokal laufen, die Failures **triagen** in:
- (a) **echte Regression** (Stunden-Logik falsch) → **Code** fixen;
- (b) **beabsichtigter neuer Wert** → Test-Erwartung/Snapshot **bewusst** anpassen.
Nicht pauschal Snapshots neu schreiben — jede Änderung begründen.

Danach passt der Round-Trip-Smoke wieder.
