# Analyse: Rechnungs- + Leistungsnachweis-Pipeline

**Datum:** 2026-06-05
**Code-Basis:** `origin/main e9a82dce`
**Scope:** Vollständige Architektur-Kartierung + bekannte Bugs + GoBD-Best-Practice-Abgleich
**Status:** Code-Analyse abgeschlossen, Live-Reproducer nicht möglich (Replit-Dev hibernated)

---

## TL;DR

Die Pipeline ist **architektonisch sauber** (Pot-Split, Cascade-Storno, Drift-Detection, ZUGFeRD), hat aber **drei bekannte Bugs** aus dem letzten Audit (29.05.2026) plus **vier strukturelle Risiken** im Storno- und PDF-Pfad. **Keine direkten GoBD-Verletzungen** — aber das System verlangt strenge Disziplin im Edge-Case-Verhalten, die laut Code teilweise nur über Tests + Audits gewährleistet ist.

## A. Architektur-Kartierung

### A.1 — Rechnungs-Generierung (`generateInvoiceCore`)

**Zentraler Pfad:** `server/services/invoice-calc.ts:300`

```
POST /api/billing/generate                          (Einzeln)
POST /api/billing/generate-all                      (Massenerstellung)
       │
       ▼
generateInvoiceCore(customerId, billingMonth, billingYear)
       │
       ├─→ buildInvoiceDraft (gemeinsame Logik mit Preview)
       │     ├─→ Customer-Stammdaten + Insurance + Abtretungsdeklaration
       │     ├─→ Pot-Split (§45b / §45a / §39+§42a / private) via Largest-Remainder
       │     ├─→ Line-Items pro Pot (mit km-Quantisierung)
       │     └─→ Storno-Refs aus früher stornierten Rechnungen
       │
       ├─→ N-Invoice-Pfad (wenn Pot-Split nötig):
       │     ├─→ EINE Rechnung pro Pot mit gemeinsamer billingRunId
       │     ├─→ Pot-spezifischer Empfänger (Kasse/Kunde)
       │     ├─→ getNextInvoiceNumberTx mit FOR-UPDATE-Lock
       │     └─→ Insert in invoices + invoice_line_items (atomar)
       │
       └─→ schedulePdfPersistInBackground (Task #544)
             └─→ persistInvoicePdf — generiert PDF + LN + ZUGFeRD-XML asynchron
```

**Wichtige Garantien laut Code:**
- ✅ **GoBD-Snapshot:** `customerName`, `recipientName/Address`, `insuranceProviderName`, `pflegegrad` werden zum Zeitpunkt der Rechnung in die Zeile geschrieben — Stammdaten-Änderungen brechen die Historie nicht.
- ✅ **Pot-Σ-Invariante:** `shared/domain/budget-invoice-split.ts` (Largest-Remainder, deterministischer `POT_ORDER`-Tiebreak).
- ✅ **Idempotenz:** vor `generate-all` Check `hasActive` blockiert Doppel-Generierung.
- ✅ **Lückenlose Nummernkreise pro Jahr:** `getNextInvoiceNumberTx` mit Tx-Lock.

### A.2 — Leistungsnachweis-PDF

**Zentraler Pfad:** `server/lib/pdf-generator.ts:499`

```
GET /api/billing/:id/leistungsnachweis
       │
       ├─→ Cache-Hit: aus Object Storage ausliefern + X-Pdf-Drift-Header
       │
       ├─→ Cache-Miss (Pflegekasse): persistInvoicePdf → reload → ausliefern
       │
       └─→ Cache-Miss (Selbstzahler): renderLeistungsnachweisOnTheFly (kein Cache)
```

**HTML-Bau:**
- `generateLeistungsnachweisHtml(data)` → Gruppierung nach `appointmentId`, dann Datum/Zeit (Task #571)
- Service-Zeilen + KM-Zeilen (`travel_km`, `customer_km`) getrennt rendern
- Selbstzahler: USt addieren auf Display-Preis; Pflegekassen-Rechnungen: USt = 0

**Concurrency-Schutz:**
- `persistInvoicePdfInFlight: Map<invoiceId, Promise>` (pdf-generator.ts:462–493) verhindert paralleles Doppel-Persistieren.
- Globale Semaphore: `PDF_RENDER_CONCURRENCY` (env-konfigurierbar).

### A.3 — Storno-Pipeline

**Zentraler Pfad:** `PATCH /api/billing/:id/status { status: "storniert", cascadeRun?: true }`

```
PATCH → allowedTransitions: entwurf/versendet/bezahlt → storniert
       │
       └─→ performStorno (in withAudit-Transaktion)
             ├─→ getInvoiceForUpdateTx (FOR-UPDATE-Lock auf Original)
             ├─→ getNextInvoiceNumberTx (neue Stornorechnung-Nummer)
             ├─→ Copy aller Line-Items mit negativen Beträgen
             ├─→ Storno-dueDate = today + N Tage (default 30, Task #562)
             ├─→ stornierteRechnungId = Original-ID
             ├─→ status = "entwurf" (nicht "versendet")
             └─→ Cascade (wenn cascadeRun=true):
                  └─→ Alle Geschwister mit gleicher billing_run_id stornieren
       │
       └─→ schedulePdfPersistInBackground für Storno-Rechnung
```

**Wichtige Garantien:**
- ✅ **Pessimistisches Locking:** Verhindert Doppel-Storno bei parallelen PATCH-Anfragen.
- ✅ **GoBD-Immutability:** Original wird NICHT überschrieben — eine NEUE Storno-Rechnung mit negativen Beträgen + Referenz wird angelegt.
- ✅ **Cascade-Atomarität:** Alle Geschwister-Rechnungen einer billing_run_id in EINER Transaktion (Task #759).
- ✅ **Storno hält LN aktiv** (Task #576): der zugehörige Leistungsnachweis wird beim Storno NICHT ungültig.
- ✅ **Re-Rechnung nach Storno:** `referencedStornoInvoiceIds`-Array verlinkt Original (Task #585).

### A.4 — Verifikation + Drift-Detection

**Drei Fingerprints:**
- `pdfDataFingerprint` (Render-Eingabedaten für Rechnung)
- `leistungsnachweisDataFingerprint` (Render-Eingabedaten für LN)
- `pdfHash`, `leistungsnachweisHash` (bytestabile sha256 der PDFs)

**Beim Abruf:** Live-Fingerprint wird neu berechnet und verglichen → `X-Pdf-Drift: true` Header, wenn Stammdaten/Positionen sich nachträglich geändert haben.

## B. Bekannte Bugs aus Audits

### B.1 — `MITTEL-1`: GoBD-Snapshot-Drift durch JOIN-Alias 🔴

**Quelle:** `docs/audits/full-app-2026/chunks/08-billing.md`

**Symptom:** `server/storage/billing-storage.ts:40` (`getInvoice`) liefert `customers.name` als Feld `customerName` und **überschreibt damit den persistierten GoBD-Snapshot `invoices.customer_name`**.

**Impact:**
- Verifier-/Re-Render-Code, der aus dem Snapshot baut, sieht den AKTUELLEN Kundennamen statt den damals festgehaltenen.
- Bei Namens-Änderung (Heirat, Korrektur) drifted die Rechnungs-Historie.
- GoBD-Risiko bei Steuerprüfung: Re-Render erzeugt eine andere PDF als die ursprünglich versendete.

**Fix-Vorschlag:** `customerName` aus dem JOIN-Mapping entfernen, immer `invoices.customer_name` (Snapshot) zurückgeben. Effort: S.

### B.2 — `MITTEL-2`: `updateInvoiceStatus` ohne Tx-Kontext 🟡

**Quelle:** `docs/audits/full-app-2026/chunks/08-billing.md`

**Symptom:** `server/storage/billing-storage.ts:111` (`updateInvoiceStatus`) nutzt `db` direkt statt eines `DbOrTx`-Parameters.

**Impact:** Wenn aus einer Batch-Transaktion aufgerufen, **bricht die Atomizität** — der Status-Update läuft in einer separaten Tx und kann teilweise persistieren, während der Rest rollbackt.

**Fix-Vorschlag:** `DbOrTx`-Parameter hinzufügen, Default `db`. Effort: S.

### B.3 — `NIEDRIG`: God-File `billing.ts` 🟢

**Stand:** Quality-Sweep 27.05.2026 zeigt 3169 LOC; aktueller HEAD `e9a82dce` zeigt **3656 LOC**.

**Impact:** Nicht review-fähig, hohes Regressions-Risiko bei Änderungen. Wachsend über Zeit.

**Fix-Vorschlag:** Refactor → `billing-service.ts` (siehe Refactor-Masterplan). Effort: L.

## C. Strukturelle Risiken (potenzielle Bugs, nicht im Audit dokumentiert)

### C.1 — PDF-Drift bei nachträglicher Daten-Änderung 🟡

**Risiko:** `X-Pdf-Drift: true` wird **nur als HTTP-Header** ausgeliefert. Ist im UI sichtbar? Wenn nicht, fällt es nur dann auf, wenn jemand den Header inspiziert.

**Was schief gehen kann:**
- Customer-Stammdaten werden korrigiert (z.B. Adresse) → bestehende Rechnungs-PDFs zeigen alten Stand (korrekt nach GoBD), aber Verifier-Re-Render würde neuen Stand produzieren → Hash-Mismatch.
- Hier verbirgt sich der `MITTEL-1`-Bug: weil `getInvoice` den aktuellen Namen statt Snapshot zurückgibt, sieht der Live-Fingerprint immer den aktuellen Stand → falsch-positive Drift-Meldung.

**Fix:** B.1 lösen + UI-Hinweis bei Drift einbauen (z.B. roter Banner "Daten haben sich seit PDF-Erstellung geändert").

### C.2 — Race-Condition bei `persistInvoicePdf` 🟡

**Beobachtung:** `persistInvoicePdfInFlight` (Map) verhindert Doppel-Persist **innerhalb eines Prozesses**.

**Was schief gehen kann:**
- Bei zwei Server-Instanzen (Replit-Auto-Scale) sieht jede Instanz nur ihre eigene In-Flight-Map → beide rendern parallel und persistieren beide.
- `loadInvoicePdfFromStorage` liest aus Object Storage; wenn beide Persistierungen abschließen, gewinnt die letzte → mögliche Hash-Inkonsistenz mit DB.
- Mitigation laut Code: GoBD-Code-Kommentar sagt `persistInvoicePdf` überschreibe kein bestehendes `pdf_path` — also kein DB-Drift. Aber das Storage-Blob könnte doppelt vorhanden sein.

**Fix:** DB-Advisory-Lock (`pg_advisory_xact_lock(invoice_id)`) am Beginn von `persistInvoicePdfInner` einbauen. Effort: S.

### C.3 — Storno: dueDate-Drift 🟡

**Beobachtung:** `stornoDueDateIso = addDays(todayISO(), 30)` setzt die Fälligkeit der **Stornorechnung** auf heute + 30 Tage.

**Was passt:**
- Storno-Rechnung ist eine neue Rechnung mit eigener Fälligkeit (richtig).

**Was missverstanden werden könnte:**
- User könnte erwarten, dass die Storno-Fälligkeit = ursprüngliche Fälligkeit (z.B. wenn Storno wegen Korrektur-Wiederabrechnung). Ist das **Anwender-Verhalten** bekannt?
- ZUGFeRD-Code BT-9 erwartet ein definiertes Datum → ok, aber semantisch zweideutig.

**Fix-Vorschlag:** UI bei Storno-Auslösung eine Wahl bieten: „Fälligkeit übernehmen" / „neue Fälligkeit (heute + 30)". Effort: S.

### C.4 — LN-PDF wird bei Selbstzahler NICHT gecached 🟡

**Beobachtung:** Im Selbstzahler-Pfad rendert `renderLeistungsnachweisOnTheFly` JEDES Mal neu. Kein Object-Storage-Cache.

**Impact:**
- Jeder Abruf des Selbstzahler-LN startet einen Puppeteer-Render (50–500 ms, je nach Hardware).
- Bei vielen Selbstzahler-Kunden → Performance-Sumpf.
- GoBD-mäßig vertretbar, da Selbstzahler-LN nicht versendet wird (nur intern), aber inkonsistent zur Pflegekassen-Pipeline.

**Fix:** Selbstzahler-Cache analog Pflegekasse aktivieren. Effort: M.

### C.5 — Datenfluss Termin → Leistungsnachweis → Rechnung 🔴

**Architektur:**
1. Termine werden geplant + dokumentiert (`POST /api/appointments/:id/document`)
2. Monatlich entsteht ein `monthly_service_records`-Eintrag (Leistungsnachweis-Datensatz)
3. LN wird **vom Kunden signiert** (oder employee_signed, dann auf customer warten)
4. `generate-all` filtert auf Records mit `status IN ('completed', 'employee_signed')`
5. Daraus entstehen Rechnungen + LN-PDFs

**Risiko Punkt 3:** Was passiert, wenn der Kunde nicht signiert, aber Mitarbeiter schon? Die `generate-all` akzeptiert beides:
```ts
or(
  eq(monthlyServiceRecords.status, "completed"),
  eq(monthlyServiceRecords.status, "employee_signed"),
)
```

**Frage:** Ist `employee_signed` ohne Customer-Unterschrift bei Pflegekassen-Abrechnung zulässig? Laut SGB-XI-Vereinbarung muss der Pflegebedürftige die Leistung quittieren. **Wenn `employee_signed` reicht für die Rechnung, riskiert das Rückforderungen der Pflegekasse.**

**Fix:** Verifizieren: bei Pflegekassen-Customers nur `completed` zulassen, `employee_signed` nur für Selbstzahler. Falls bereits so, dann dokumentieren. Effort: S.
