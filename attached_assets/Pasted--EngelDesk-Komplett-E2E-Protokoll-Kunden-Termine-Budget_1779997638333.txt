**Reproducer:** 4 PUTs auf `/api/budget/:cid/type-settings` mit unterschiedlichen `validFrom` (2026-06-01: 65,50€ → 2026-08-01: 80€ → 2026-10-01: 100€ → 2027-01-01: 131€).

**Erwartet:** 4 Settings-Zeilen für §45b, die ersten 3 mit `validTo` der jeweiligen Folge-Phase, eine offen.

**Ist:**
```json
[{"limit":13100,"validFrom":"2027-01-01","validTo":null,"enabled":true}]
```

🔴 **Nur 1 Zeile — die letzte. Die ersten 3 Phasen sind verloren.**

**Folge BUG-13 (NEU entdeckt):** Anschließend Versuch eines „Reset"-PUT ohne `validFrom`:
```javascript
PUT /api/budget/:cid/type-settings  // ohne validFrom für §45b
→ 200 OK
// Aber:
GET /api/budget/:cid/type-settings →
  [{limit:13100, validFrom:'2027-01-01', validTo:null, enabled:true}]   ← UNVERÄNDERT
```

Die bestehende Zukunfts-Zeile bleibt unverändert. Folge: Topf-Stand `avail=30000` (nur Carryover, **kein monthly_auto** für Mai 2026, weil für Mai keine aktive Settings-Zeile existiert). Die App ist quasi „in der Zukunft eingefroren".

## Neue Bugs (BUG-13 + BUG-14) im Detail

### 🔴 BUG-13 NEU: `PUT /type-settings` ohne `validFrom` ändert bestehende Zukunfts-Zeile nicht

**Symptom:** Auf einen Kunden mit einer bestehenden Settings-Zeile, die `validFrom` in der Zukunft hat (z.B. nach BUG-9-Sequenz), wirkt ein PUT ohne `validFrom` NICHT:
- Die alte Zeile bleibt mit ihrem zukünftigen `validFrom`
- Der Kunde hat im AKTUELLEN Zeitraum (Mai 2026) KEINE aktiven Settings
- Folge: `monthly_auto` greift nicht, `avail` zeigt nur was an Carryover/initial_balance vorhanden ist

**Erwartet:** Entweder
- (a) Die alte Zukunfts-Zeile wird auf `validTo=neueValidFrom-1` geschlossen und die neue Zeile mit `validFrom=heute` angelegt, oder
- (b) Die neue Zeile bekommt `validFrom=heute` automatisch und schließt die alte mit `validTo=heute-1`

**Code-Anker:** `server/storage/budget/preferences-storage.ts` — `upsertBudgetTypeSettings`. Vermutlich macht die Funktion einen UPSERT mit `WHERE validTo IS NULL`-Lookup, der die Zukunfts-Zeile als „offen" findet und nicht überschreibt.

**Reproducer:**
```javascript
// Schritt 1: lege eine Zukunfts-Settings-Zeile an
await fetch('/api/budget/'+cid+'/type-settings', {method:'PUT', credentials:'include', headers:H, body: JSON.stringify({
  settings:[{budgetType:'entlastungsbetrag_45b', enabled:true, priority:1, monthlyLimitCents:13100, validFrom:'2027-01-01'}]
})});

// Schritt 2: versuche „jetzt gültige" Settings ohne validFrom
await fetch('/api/budget/'+cid+'/type-settings', {method:'PUT', credentials:'include', headers:H, body: JSON.stringify({
  settings:[{budgetType:'entlastungsbetrag_45b', enabled:true, priority:1, monthlyLimitCents:13100}]
})});

// Schritt 3: prüfe Settings
const s = await fetch('/api/budget/'+cid+'/type-settings', {credentials:'include'}).then(r=>r.json());
console.log(s.filter(x=>x.budgetType==='entlastungsbetrag_45b'));
// IST: [{limit:13100, validFrom:'2027-01-01', validTo:null}]   ← unverändert
// SOLL: [{limit:13100, validFrom:'2026-05-28', validTo:'2026-12-31'}, {limit:13100, validFrom:'2027-01-01', validTo:null}]
```

### 🔴 BUG-14 NEU: Reversal-Buchungen haben `hauswirtschaftCents = null`

**Symptom:** Beim Storno eines Termins werden reversal-Transaktionen mit `amountCents = +abs(orig)` korrekt angelegt, aber die Service-Cent-Spalten (`hauswirtschaftCents`, `alltagsbegleitungCents`, `travelCents`, `customerKilometersCents`) sind **alle null**. Die korrespondierende consumption-Buchung hatte sie korrekt gefüllt.

**Reproducer auf Kunde 164086 (8h Hauswirtschaft):**
```javascript
// Nach Storno:
const tx = await fetch('/api/budget/'+cid+'/transactions',{credentials:'include'}).then(r=>r.json());
const reversals = tx.filter(t=>t.transactionType==='reversal' && t.appointmentId===288179);
console.log(reversals);
// IST: [{amt:+20000, alloc:118663, hauswirtschaftCents:null, rev:423465}, {amt:+10400, alloc:118662, hauswirtschaftCents:null, rev:423466}]
// SOLL: hauswirtschaftCents:20000 (bzw. 10400) — Spiegelbild der consumption
```

**Folge:**
- Drift-Detektor „Σ hauswirtschaftCents nach Storno = 0" wäre rot (`20000 + 10400 + null + null = 30400 ≠ 0`)
- Lexware-Export aggregiert die Bein-Spalten und sieht den Storno nicht
- Statistiken zeigen Hauswirtschafts-Verbrauch trotz Storno

**Code-Anker:** `server/storage/budget/consumption-engine.ts` und/oder `server/storage/budget/rebook-storage.ts` — Funktion, die reversal-Transaktionen schreibt. Vermutlich werden die Service-Cent-Spalten nicht aus der zu reversierenden Transaktion kopiert.

**Fix-Vorschlag:** Beim Anlegen der reversal-TX die Service-Cent-Spalten der originalen consumption-TX spiegeln (mit umgekehrtem Vorzeichen — sie sind als positive Werte gespeichert, beim Storno auch positiv):
```typescript
// vor Insert:
reversal.hauswirtschaftCents = orig.hauswirtschaftCents;
reversal.alltagsbegleitungCents = orig.alltagsbegleitungCents;
reversal.travelCents = orig.travelCents;
reversal.customerKilometersCents = orig.customerKilometersCents;
reversal.hauswirtschaftMinutes = orig.hauswirtschaftMinutes;
// etc.
```
